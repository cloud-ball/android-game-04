# Shrink the tower to 88-unit cells

Stack Drop should draw each cell at **88 canvas units: about 34 dp, 5.6 mm, or 103 physical pixels on the 1260 x 2800 test phone**. At that size the 9 x 18 well is about **73% of screen width and 66% of screen height**. The current build makes the well about 98% of the width. Three fixes go with the new size. First, switch the camera from a 30° perspective lens to an **orthographic camera locked to width, pitched 9°**. Second, make the cubes thin **0.55-deep gem slabs**. Third, rebuild the hexagonal base so it fits inside the side margins. The "chunky" look and the cropped pedestal share one root cause in the code. `blocks_view.gd` frames the camera so the 9-wide well nearly fills the screen and explicitly allows the base to "run off the bottom edge". The hex base itself is about 15 cells wide, 1.7 times the well, so with the well that large it cannot fit on screen. Readability then rests on lightness contrast, a dark gap, and a per-type glyph, not on large cubes. The HUD moves out of the well into a read-only top band (score, CPU mini-board, NEXT strip) and a tappable bottom band (HOLD). The garbage meter sits against the well's left edge, where the player is already looking. No published source gives a measured board-to-screen ratio or camera spec for this genre. The sizes below come from geometry, Android and Apple platform rules, and accessibility guidance, and an on-device A/B test at 84, 88 and 95 units should settle the final value.

## A full-width well is what makes the cubes chunky and crops the base

Portrait phones are too narrow for this board. A 9 x 18 well has a 1:2 aspect ratio, while a 20:9 screen is 0.45 wide per unit of height. Width therefore always runs out first. Filling the width gives 45.7 dp cells and a well 90% of the screen tall, with nothing left above or below. The genre norm of a 10-wide, 20-visible well has the same shape, and 9-wide wells are an established variant ([Tetris Wiki: Playfield](https://tetris.wiki/Playfield)). The code confirms that this is the current configuration. The constants in `games/blocks/scenes/blocks_view.gd` are `FOV_DEG = 30`, `PITCH_DEG = 7`, `CUBE = 0.94`, `SIDE_BAND = 0.012` and `TOP_BAND = 0.085`. The camera fit only tests the well's ±4.85-unit width and comments that "the hex base may run off the bottom edge". The base is a 6-sided cylinder of radius **7.2-7.6 units (about 15 cells point to point)**, so at near-full-width framing it gets clipped on both sides and at the bottom.

Touch rules do not force big cells, because cells are never tapped individually. Android's **48 x 48 dp minimum with 8 dp spacing** applies to things the player taps ([Google Accessibility Help](https://support.google.com/accessibility/android/answer/7101858)). Hit rates fall off sharply below about 7-10 mm, and edge targets need 9-12 mm ([Hoober, UXmatters 2017](https://www.uxmatters.com/mt/archives/2017/07/design-for-fingers-touch-and-people-part-3.php)). Falling-block pieces are moved by relative swipes and taps anywhere on screen ([falling-blocks README](https://github.com/Clyde098/falling-blocks)). Cell size is therefore a question of how big things look, plus how far the finger travels per column. That second factor can be decoupled from cell size altogether.

The 1080-unit canvas makes the conversion easy. The project uses `canvas_items` / `expand` stretch, so the canvas is always 1080 units wide and a 20:9 phone gets a 1080 x 2400 canvas. **Canvas units per dp = 1080 / screen width in dp** ([platform notes, Android dp definitions](https://developer.android.com/guide/topics/ui/accessibility/apps)). The research notes disagree about the test phone. One set assumes 411 dp (3.06 px/dp) and the other points out that 1260-px panels usually ship at density 480, which gives 420 dp. The canvas-unit and millimetre values below hold either way, because on a given panel a canvas unit is a fixed physical size (about 0.064 mm here). Only the dp labels move by about 2%. Run `adb shell wm density` before quoting dp.

| Cell (canvas units) | dp (411-420 dp phone) | mm | Well W, % of screen | Well H on 2400, % | Verdict |
|---|---|---|---|---|---|
| 79 | 30 | 5.0 | 66% | 59% | Too small for facet detail |
| 84 | 32 | 5.4 | 70% | 63% | Lower bound of A/B |
| **88** | **34** | **5.6** | **73%** | **66%** | **Recommended** |
| 95 | 36 | 6.0 | 79% | 71% | Upper bound; NEXT must go above the well |
| 110 | 42 | 7.0 | 92% | 83% | Reproduces today's chunky look |

The recommended 88-unit cell is 103 px wide on the Vivo. That leaves room for a 6% gap (about 6 px) and a 10% bevel band (about 10 px), well above the roughly 3-px point where gaps start to shimmer under MSAA. The full 9-column width is 51 mm, which also stops the outer columns from sitting inside Android's left and right back-gesture zones. Those zones take priority over app input on Android 10+ ([Android Developers: edge-to-edge](https://developer.android.com/develop/ui/views/layout/edge-to-edge)).

Use a fixed physical drag step per column rather than one cell-width per column. **36 dp per column (about 6 mm, 95 units on the Vivo)** is a good default, with a 28-48 dp slider. Players complain that drag-to-move "often let[s] you down" ([Gamezebo](https://www.gamezebo.com/reviews/tetris-battle-drop-review-get-used-to-it/)) and describe swipe controls as "slow, clunky" ([TouchArcade](https://toucharcade.com/community/threads/puzzle-games-with-precise-controls.312950/)). With a fixed step, the board can shrink without making drags any longer.

## An orthographic camera at 9° makes every cell identical

The chunkiness has a measurable cause in the camera. Perspective depends only on where the camera sits relative to each cube, not on the lens ([PhotoShelter](https://blog.photoshelter.com/2018/06/a-mathematician-weighs-in-on-lens-compression/)). With the current 30° FOV, 7° pitch and a pushed-in camera, the top rows are seen slightly from below. The bottom rows are seen from about 22° above, which exposes a **0.38-cell top face** on a 0.94-deep cube. The top rows also render about **6.8% larger** than the bottom rows. Those figures are geometry derived in the notes, not measurements. The result is a cube that changes shape as it falls. Godot's orthographic projection keeps on-screen size constant at any distance, and its docs note that 3D games that "look 2D" often use it ([Godot Camera3D](https://docs.godotengine.org/en/stable/classes/class_camera3d.html)).

| Setting | Current | Recommended (primary) | Fallback if it reads too flat |
|---|---|---|---|
| Projection | Perspective, FOV 30°, `KEEP_HEIGHT` | `PROJECTION_ORTHOGONAL`, `keep_aspect = KEEP_WIDTH` | Perspective, `KEEP_WIDTH`, horizontal FOV ≈ 8.8° at distance 80 |
| Scale | Fit search | `size = 1080 / cell_units` (12.27 world units at 88) | Distance d where 2·d·tan(fov/2) = 12.27 |
| Pitch | 7° | **9°** (range 6-10) | 5-7° |
| Top/bottom row size difference | ~6.8% | 0% | <3% |
| Visible top face per cell | 0 to 0.38 cell | 0.55 × sin 9° ≈ **0.09 cell (~9 px), uniform** | ~0.05-0.15 cell |
| near / far | 0.05 / 300 | 10 / 100 at distance 50 | d−20 / d+40 |

`KEEP_WIDTH` matters on its own. With the default `KEEP_HEIGHT`, a taller 21:9 phone gets a narrower horizontal view, so a board limited by width gets clipped at the sides. With `KEEP_WIDTH`, extra height turns into headroom instead ([Godot Camera3D](https://docs.godotengine.org/en/stable/classes/class_camera3d.html)). In orthographic mode one world unit equals one cell, so `size = 1080 / cell_units` gives exactly 88 canvas units per cell on every phone. That also makes layout testable. To place the well, aim the camera at the well centre offset along the camera's up axis by `(well_centre_canvas_y − canvas_h/2) / cell_units` world units. This replaces the iterative `fit_camera` search with a closed form. The steelman case for perspective is that the existing idle sway (a small rotation about Y) gives more parallax. Orthographic keeps a diorama depth through lighting, rim highlights and the sway itself, and photographers' advice that "a slight bit of convergence is desirable" ([Cambridge in Colour](https://www.cambridgeincolour.com/tutorials/tilt-shift.htm)) argues for the long-lens fallback only if shot review finds the tower lifeless. Lens shift via `PROJECTION_FRUSTUM` and `frustum_offset` is a third option ([Godot Camera3D](https://docs.godotengine.org/en/stable/classes/class_camera3d.html)), but its units were not confirmed, so it is the riskiest of the three.

The cheapest way to reduce chunkiness is to make the cells thinner. **Scale cell depth to 0.55 (range 0.4-0.6) while keeping the face at 0.93 x 0.93**, which gives a 7% gap. Every visible side face shrinks with the depth, and the bevel and lighting still show the solidity. Set the bevel or edge band to **8-12% of the face**. Bigger bevels look like rounded candy and smaller ones disappear. The existing shader edge `smoothstep(0.82, 0.97, mid)` already falls in that range. Light the top and left rims about 25 L* brighter and the bottom and right rims darker, rather than brightening every edge, because uniformly bright edges merge into a white grid. A shading-only bevel changes shading but not silhouette and breaks if the radius gets too large ([Blender Bevel node](https://docs.blender.org/manual/it/dev/render/shader_nodes/input/bevel.html); [Arnold round edges](https://help.autodesk.com/cloudhelp/ENU/AR-3DSMax/files/arnold-3dsmax/ax-tutorials/ax-shading/arnold_for_3ds_max_ax_shading_ax_round_edges_shading_html.html)). For 162 cells, a one-segment bevelled mesh of 50-100 triangles in a MultiMesh is also fine. Godot's automatic instancing works "only in Forward+", while a MultiMesh is "a single draw primitive" ([Godot: optimizing 3D](https://docs.godotengine.org/en/stable/tutorials/performance/optimizing_3d_performance.html); [Godot: MultiMesh](https://docs.godotengine.org/en/stable/tutorials/performance/using_multimesh.html)).

## A pedestal sized to the margins stands the tower up

The base should fit inside the side margins, not exceed them. Inside 42-unit (16 dp) side margins the widest object can be 996 units, or **11.3 cells**. Use a **6-sided prism of radius 5.2 (10.4 cells, about 915 units, point to point, with points along ±X), scaled to 0.33 in Z (about 3 cells deep), 0.5 cells tall**, sitting 0.5 cells below the bottom row. Seen from 9° above, it shows a faceted front and a thin top sliver about one cell (85-90 units) tall on screen. A regular hexagon this wide would be 9 cells deep and show a 1.4-cell top face, which would eat the bottom band. Next, pull the camera's bounds test out to include the pedestal's full extent and the contact shadow. A half-cut base reads as a framing error because the rest of the object's outline is complete. A deliberate crop would have to remove a third or more of it. That threshold is a composition judgement, not a sourced number. Composition guides warn that too little negative space feels cramped and too much weakens the subject ([Envato Tuts+](https://photography.tutsplus.com/articles/10-rules-for-better-shot-composition-framing-in-photography-and-film--cms-108492)). Headroom is the buffer that keeps the eye from feeling crowded at the top ([Brainbound](https://www.brainbound.blog/headroom-photography-composition-guide)).

Grounding comes from a short stack of cheap effects. First, a single unlit quad under the pedestal with a radial gradient: about **1.3 times the pedestal's width**, 45-55% opacity at the centre fading to zero. Blob shadows like this cost "2 draw calls and few verts" on mobile, while real-time shadows are expensive there ([Game Developer: fake shadows](https://gamedeveloper.com/design/implementing-fake-shadows-in-unity-for-mobiles); [Unity Learn](https://learn.unity.com/tutorial/shadows-3224)). Second, AO baked into the pedestal's vertex colours where the plate and the posts meet it. Third, a visible break between the top plate (currently `w + 0.6` by 1.6 deep, in a lighter violet) and the hex: a gap or step of about 0.05 units plus a clear jump in lightness, because the "jammed" look comes from the two sharing a silhouette edge at similar values. Fourth, depth fog (`FOG_MODE_DEPTH`, begin about 2 units behind the pedestal, end about 20, curve 1.5-2, `fog_sky_affect` 0-0.3) so the floor fades into the background gradient. Fog is supported on the Mobile renderer. SSAO, SSR and volumetric fog are not ([Godot renderers](https://docs.godotengine.org/en/stable/tutorials/rendering/renderers.html); [Godot Environment](https://docs.godotengine.org/en/stable/classes/class_environment.html)). Environment has no vignette property, so add a radial-gradient `TextureRect` at **15-25% edge darkening** on a CanvasLayer, not a screen-reading shader ([Godot Environment](https://docs.godotengine.org/en/stable/classes/class_environment.html)). Turn off directional shadow casting on the cells. Against an opaque back pane they add cost and little else.

## Lightness, a dark gap and a glyph carry gem readability

At 88 units, three things decide whether a gem reads: **lightness contrast, a dark gap that works as an outline, and a per-type glyph**. Facet sparkle and bloom matter much less. Bugnet's rule, "most readability failures are value failures", makes a grayscale screenshot the first check ([Bugnet](https://bugnet.io/blog/readable-game-art-why-clarity-beats-detail)). Game Accessibility Guidelines asks for colour to be a backup to shapes or symbols, and notes that red/green deficiency affects about 8-10% of males ([GAG](https://gameaccessibilityguidelines.com/ensure-no-essential-information-is-conveyed-by-a-colour-alone/)). The Okabe-Ito colour-blind-safe hues are a good starting point ([NYU Siegal lab](https://siegal.bio.nyu.edu/color-palette/)). Used raw, though, they fail the grayscale test. Computed CIE L* values show sky blue (69.8) and orange (70.6) almost identical, and vermillion (54.2) and bluish green (57.7) only 3.5 apart. The table below keeps each hue and adjusts its lightness into a ladder about 8 L* apart. It is computed in CIELAB and checked against an opaque back pane of `#13192C`.

| Piece (current gem) | Hue family | Target L* | Suggested face | Face vs pane | Glyph |
|---|---|---|---|---|---|
| B square (topaz) | yellow | 90 | `#F3E745` | 13.6:1 | dot |
| F hook (aquamarine) | sky blue | 82 | `#9CD3F9` | 10.9:1 | ring |
| C tee (amethyst → amber) | orange | 74 | `#F1A815` | 8.6:1 | chevron |
| G hook (rose quartz) | reddish purple | 66 | `#DA86B4` | 6.7:1 | diamond |
| E skew (ruby) | vermillion | 58 | `#E16811` | 5.1:1 | diagonal |
| D skew (emerald) | bluish green | 50 | `#238665` | 3.9:1 | cross |
| A long (sapphire) | blue | 43 | `#186AA3` | 3.0:1 | bar |
| Garbage | desaturated slate | ~30 | `#41465C` | 1.9:1 (rim + hatch carry it) | hatch |

With this ladder every gem's face reaches the **3:1 non-text contrast** WCAG requires for graphics ([W3C SC 1.4.11](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html)). The only renaming is amethyst to amber, because purple sits too close to both the blue and the rose under deutan and protan simulation. Draw glyphs from one small atlas indexed through MultiMesh custom data, at about 40% of the cell. Make them a 15-25% value shift, not a new hue. Make the back pane **opaque**. Transparent surfaces are "particularly bad for fill rate", especially where they overlap ([Godot GPU optimization](https://docs.godotengine.org/en/stable/tutorials/performance/gpu_optimization.html)). Keep the "glass" effect to a fresnel rim on the frame. Use Filmic or AgX tone mapping rather than ACES, which "desaturates bright values". Keep `glow_hdr_threshold` above the brightest resting gem so bloom fires only on line clears ([Godot Environment](https://docs.godotengine.org/en/stable/classes/class_environment.html)). Draw the ghost piece as an outline only, in its own small MultiMesh.

## The top band is for reading, the bottom band for tapping, and the well stays clear

No published source endorses putting HUD over the well. A publishing standard rejects layouts where UI covers an element in a way that "interferes with reading the element" ([Yandex Games 1.10](https://yandex.com/dev/games/doc/en/requirements/1/10)). In this genre the top rows are where the spawn and top-out happen, which is exactly what the see-through side panels from commit 8e9ad99 cover. Genre sources list the HUD's contents but fix no positions, and they put the next queue near the spawn "just above the Matrix" ([Hard Drop wiki](https://harddrop.com/wiki/Game_interface)). A portrait-only mobile game stacks its 3 next pieces above the board ([App Store listing](https://apps.apple.com/is/app/tetris-basic/id6748584524)). Accessibility guidance says temporary warnings belong in the player's eye-line, while persistent readouts can sit at the screen edges ([GAG eye-line](https://gameaccessibilityguidelines.com/avoid-placing-essential-temporary-information-outside-the-players-eye-line/)). Apple asks for frequent controls near the thumb and menus at the top ([Apple HIG: Game controls](https://developer.apple.com/design/human-interface-guidelines/game-controls)). In Hoober's field study, 49% of people held the phone one-handed ([Hurff, Game Developer](https://gamedeveloper.com/design/how-to-design-for-thumbs-in-the-era-of-huge-screens)). Together these give a clear split: read-only information high, the HOLD tap low, and the garbage alert against the well. Side columns for NEXT do not fit. A 4-wide preview at 50% scale is about 176 units, and each gutter is only 130.

The layout below is in canvas units on a 1080 x 2400 canvas. **T** is the runtime safe-area top plus 16. It is 116 when the safe area reports about 100, which matches a 24-50 dp punch-hole band ([AOSP display cutouts](https://source.android.com/docs/core/display/display-cutouts)). The bottom limit **B** is the canvas height minus max(runtime bottom inset, 84), minus 16, which gives 2300.

| Element | x | y | Size (visual / hit) | Notes |
|---|---|---|---|---|
| Side margins | 0-42, 1038-1080 | all | 42 (16 dp) | No tappables; no gesture starts |
| CPU mini-board | 42-150 | T to T+262 | 108 x 216 board (12-unit cells, ~14% scale) + 36 caption | Display only; outline-only cells against the dark plate |
| Status row: SCORE / LINES · LEVEL | 170-880 | T to T+120 | Caption 36, score 72, values 52 | 70-80% dark plate, 3-unit outline on numerals |
| Pause | 942-1038 | T+12 | 96 visual / **144 x 144 hit** | Top-right, diagonally opposite HOLD |
| NEXT strip | 170-1038 | T+132 to T+262 | 1st preview at 60% (53-unit cells, box 220 x 124) centred near x = 540; 2nd and 3rd at 45% (40-unit cells) | Directly above the spawn columns |
| Well + posts | 130-950 (cells 144-936) | T+278 to T+1862 | 88-unit cells, 1584 tall | Centre at about 49% of screen height |
| Garbage meter | 94-124 | well height | 30 wide (0.35 cell), 88 units per pending line | Yellow → orange → red; pulse the well frame when lines arrive |
| Pedestal + shadow | ~82-998 | T+1862 to T+2002 | ~140 tall | Counts as thumb-rest/gesture area |
| HOLD | 42-258 | B−160 to B | 200 x 150 visual / **216 x 168 hit** | 45% piece preview; press glow extending 8-12 units past the box; mirror option |
| Bottom keep-out | full width | below B | ≥ 84 + 16 | Background only; reject gestures that start here |

The touch and text sizes use the narrowest common phone, 360 dp, where 1 dp = 3.0 units. That way the minimums hold on every device. The **144-unit hit area is 48 dp at worst and 55 dp (9.2 mm) on the Vivo**, with **at least 24 units** between targets ([Google Accessibility Help](https://support.google.com/accessibility/android/answer/7101858); [Apple HIG: Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)). The HOLD target is larger because practitioners size the main in-play action at 64-80 dp ([h-idris](https://h-idris.com/blog/mobile-game-ui-design.html)). Captions are at least **36 units** (12 sp; Android's body floor is 12 sp and labelSmall is 11 sp) ([Android Design: Accessibility](https://developer.android.com/design/ui/mobile/guides/foundations/accessibility); [M3 type tokens](https://raw.githubusercontent.com/material-components/material-components-android/master/lib/java/com/google/android/material/typography/res/values/tokens.xml)). Score digits are **72 units**. That matches XAG 101's mobile minimum of 18 px at 100 DPI scaled linearly, about 4.6 mm body height or 72 units on this panel ([XAG 101](https://learn.microsoft.com/en-us/gaming/accessibility/xbox-accessibility-guidelines/101)). Banners are **104 units**, and countdown or KO text is **144 units**, XAG's "large text" size, where 3:1 contrast is acceptable ([XAG 102](https://learn.microsoft.com/en-us/gaming/accessibility/xbox-accessibility-guidelines/102)). Smaller HUD text needs 4.5:1 against the lowest-contrast area behind it ([XAG 102](https://learn.microsoft.com/en-us/gaming/accessibility/xbox-accessibility-guidelines/102)). White text over a white crystal flash needs a black plate of **at least 79% opacity** for 4.5:1, a figure derived from the WCAG luminance formula. Apple and XAG both ask for text scaling up to 200% ([Apple HIG: Accessibility](https://developer.apple.com/design/human-interface-guidelines/accessibility)). The 120-unit status row cannot hold 200%, so an in-game 100/125/150% text option for the HUD, with 200% for menus and banners, is the realistic compromise.

Read the safe area at runtime, never hardcode it. Since Android 15, apps targeting SDK 35 are forced edge-to-edge, and on Android 16 with target SDK 36 the opt-out is gone ([Android 16 behaviour changes](https://developer.android.com/about/versions/16/behavior-changes-16)). Play has required SDK 36 for updates since 2026-08-31 ([Play Console Help](https://support.google.com/googleplay/android-developer/answer/11926878?hl=en-419)). On start and on every `size_changed`, call `DisplayServer.get_display_safe_area()` and `get_display_cutouts()` and convert pixels to canvas units with `1080 / screen_px_width` ([Godot Android export](https://docs.godotengine.org/en/stable/classes/class_editorexportplatformandroid.html)). Then take the maximum of each runtime inset and a floor: top 0 (+16 padding), sides 42, bottom 84 (32 dp). Gesture zones still apply under `immersive_mode` ([Android Developers: edge-to-edge](https://developer.android.com/develop/ui/views/layout/edge-to-edge)). Use a flick down for hard drop rather than a swipe up, since swipes up from the bottom edge get confused with taps and the home gesture ([itch.io comment](https://itch.io/post/12727791)). Compute the cell size as `min((1080 − 2·130)/9.32, H_avail/18)`, clamped to 30-38 dp, where 9.32 is cells plus posts. On 19.5:9 this drops to about 85 units. On 16:9 the height limit applies, and NEXT can move to a side column whenever a gutter is wider than 2 x (4 x 0.5 cell) + margin.

## Conclusion

The real fix is to stop sizing the board from the screen and size it from the cell. Once 88 units is the fixed point, an orthographic camera turns layout into arithmetic that can be unit tested. The board, the HUD, the pedestal and the safe area then become rectangles in one pure layout class rather than the result of a camera search. That fits the project's rule that logic lives in testable, Node-free classes. It also means a new aspect ratio means adding a test case, not retuning by eye. The cropped base turned out to be a scale mismatch, a pedestal 1.7 times the tower's width, not a framing tweak. That suggests checking every decorative 3D element against the layout's width budget, not just the play field.

The answers that are still open are empirical, not theoretical. No source measures preferred cell size, board-to-screen ratio or camera settings for this genre, so 88 units is a defensible starting point to test, not a standard. The Vivo's actual density, how Godot's safe area behaves under immersive mode with gesture navigation, and whether orthographic looks too flat in motion can all only be settled on the phone. Settle them with the A/B test before polishing gem shading. Shading changes are cheap to redo; layout changes ripple through the HUD.
