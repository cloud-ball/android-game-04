# Content pipeline for 36+ golf holes (Fairway Flick, Godot 4.7, one dev plus an AI assistant)

Context checked in the repo before researching: `games/golf/logic/hole_data.gd` already holds the runtime form: vertex heights on a uniform grid with 0.5-1 m cells, one `Surface` byte per cell (OUT, TEE, FAIRWAY, ROUGH, FRINGE, GREEN, SAND, WATER, PATH), tee, pin and par. Each cell is two triangles split along the (i,j)->(i+1,j+1) diagonal, the same as the render mesh. The earlier design report (`docs/research/Fairway Flick golf game design.md`) already proposed "tiles in the editor, heightfield at runtime, validator in tests", greens with cup zones at 0-3%, shoulders at 4-8%, shedding ramps above about 9%, and 18-30 m greens. These notes go deeper on the authoring and bake pipeline that has to scale from 9 holes to 36 or more.

## How do shipped golf games with course designers/editors build courses?

### Takeaway
Shipped editors follow two patterns. Console designers use "generate from a few parameters, then edit": routing waypoints, brushed or splined surfaces, sculpting and stamped bunkers. AAA real-course pipelines turn source data into a heightfield plus material masks and edit them non-destructively. A small open-source golf game shows the cheapest version: model in Blender, bake the surface type and height into one small image, and keep a text file per hole with tee, pin, target and par. Hole models are shared across holes by moving tees and pins.

### Cited Findings
**Console course designer (PGA TOUR 2K21-2K25, HB Studios)**
- New-course flow in 2K25: name the course, set the generation options **theme, terrain and layout**, then Continue, and a course is generated — [PGA TOUR 2K25 Course Designer](https://pgatour.2k.com/2k25/up-your-game/course-designer/)
- Routing edit: the Cursor tool grabs a hole's tee, green or hole-number waypoint and drags it, which "changes a hole's flow and direction" — [PGA TOUR 2K25 Course Designer](https://pgatour.2k.com/2k25/up-your-game/course-designer/)
- Sculpt tools raise and lower ground and flatten fairways and greens. Spline tools make lakes and rivers. A "High Resolution Terrain" option gives a denser mesh for finer sculpting with fewer unwanted edges — [PGA TOUR 2K25 Course Designer](https://pgatour.2k.com/2k25/up-your-game/course-designer/)
- Terrain Painting (new in 2K25) has 4 layers (Grass/Topsoil, two Sub-Soil, Bedrock), each textured as Rock, Sand, Dirt or Natural Area. Two extra standard surface layers can be customised (mulch, pine straw, cart path) — [PGA TOUR 2K25 Course Designer](https://pgatour.2k.com/2k25/up-your-game/course-designer/)
- Bunkers are **stamped**, with parameters for depth, lip depth, lip start and lip steepness. An **Edge Blending** slider blends where two surfaces meet. "Surface Weathering" adds slight browning for variation — [PGA TOUR 2K25 Course Designer](https://pgatour.2k.com/2k25/up-your-game/course-designer/)
- Per-hole options: green speed, fairway firmness and rough parameters, set from a hole waypoint. **Up to 4 pin positions per hole.** The guide tells designers to playtest for unplayable areas and for spots much harder than the rest of the course — [PGA TOUR 2K25 Course Designer](https://pgatour.2k.com/2k25/up-your-game/course-designer/)
- 2K23 made splines easier to tweak "to further fine tune the surfaces", and added splined fences, trees, bushes and objects — [PGA TOUR 2K23 Course Designer](https://pgatour.2k.com/2k23/up-your-game/course-designer/)
- 2K21-era guide: the designer auto-generates a course on entry, and those auto courses "are generally really badly designed". Greens and fairways can be **brushed** (pre-made shapes dropped in) or **splined** (custom outline). Generated fairways can come out bumpy and need sculpting flat — [Game Rant PGA 2K21 design guide](https://gamerant.com/pga-2k21-design-course-guide/)

**AAA real-course pipeline (EA SPORTS PGA Tour, Frostbite)**
- Courses were LiDAR-scanned. Procedural software converted the point data into **heightfield maps and masks**, which were imported into the Frostbite editor — [EA: Procedural terrain in EA SPORTS PGA Tour](https://www.ea.com/news/procedural-terrain-in-ea-sports-pga-tour)
- Raster layers ("overlays") drive terrain changes. Heightfield data in overlays decides when to switch masks. Artists see the terrain update live while placing stones and trees. Bunker depth is adjusted in-editor without re-export. Noise layers generate wet-sand and dry-grass variation. The workflow is non-destructive and "saved weeks". The game shipped 28 courses, and the tools are shared by 7 EA titles (Battlefield 2042 maps use hundreds of interdependent overlays). Source talk: Julien Keable, GDC 2023, "From Battlefields to Fairways" — [EA](https://www.ea.com/news/procedural-terrain-in-ea-sports-pga-tour)

**Small open-source golf game (Super Video Golf / VGA Golf, crogine engine)**
- Holes are modelled in Blender from `hole_template.blend` and must fit **320 x 200 m** (1 unit = 1 m). Recommended green radius is **about 5-6 m**, because bigger greens lead to long putts. Required surfaces: at least fairway and green. Scrub around the edge marks out-of-bounds — [VGA Golf: Creating your own courses part 1](https://fallahn.itch.io/vga-golf/devlog/349460/creating-your-own-courses-part-1)
- Surface type is painted as **vertex colour** in grey steps of 10: rough 5, fairway 15, green 25, bunker 35, water 45, scrub 55, stone 65 (0-255). Each terrain type also needs its own material, because the engine splits the mesh by material and reads vertex colour for collision — [VGA Golf part 1](https://fallahn.itch.io/vga-golf/devlog/349460/creating-your-own-courses-part-1)
- The bake produces a **320 x 200 px RGBA PNG**: the red channel is terrain type and the green channel is an optional heightmap of the surrounding landscape (blue and alpha are unused, but RGBA is required). The same texture drives in-game generated vegetation — [VGA Golf: Creating your own courses part 2](https://fallahn.itch.io/vga-golf/devlog/349502/creating-your-own-courses-part-2)
- Tee, pin and `target` (initial aim direction) are Empties snapped to the surface. They are exported to a text `.hole` file that references a hole model. **Several `.hole` files can share one model with different tee and pin positions. One 18-hole course uses only two models.** A `course.data` text file lists the holes in play order, plus skybox, billboard vegetation model and sprites, and audio. Listing a subset makes a front-nine or back-nine variant — [VGA Golf part 2](https://fallahn.itch.io/vga-golf/devlog/349502/creating-your-own-courses-part-2)
- Par rule of thumb: **par = minimum strokes to reach the green + 2**, then playtest and edit — [VGA Golf part 2](https://fallahn.itch.io/vga-golf/devlog/349502/creating-your-own-courses-part-2)

**Seeded procedural mini golf (MiniGolf Endless MMO, indie)**
- Seeds the RNG from the hole number. It carves a narrow fairway path, then widens it by replacing each path point with a fairway circle of random radius. It converts random fairway and rough cells into bunkers and water, then **pushes a fairway path back through the water** so every hole stays completable — [ModDB: MiniGolf Endless MMO](https://www.moddb.com/games/minigolf-endless-mmo) (page returned 403 when fetched in this session. The description comes from the search-engine summary of that page and matches the citation in the earlier repo report.)

**Routing research**
- A 2022 TU Delft MSc thesis (W.R. Morssink) frames whole-course routing as constraint satisfaction: regulations, safe spacing between holes, diversity. An exact constraint-programming model "struggles with exponential computation"; the thesis compares it with random search (holes 1-9, then the rest) and with a genetic algorithm that mutates and crosses hole layouts — [TU Delft repository](https://repository.tudelft.nl/record/uuid:4007f5ae-cd6e-45a5-9cbc-e5d50e82ef35)

### Inferences
- The recurring shape across 2K, Frostbite and VGA Golf is **parametric description -> raster bake (height + surface mask) -> non-destructive tweaks -> playtest**. Fairway Flick's HoleData already is the raster end. The missing piece is a parametric "HoleSpec" layer above it that can be regenerated at any time.
- 2K's useful primitives, in order of payoff: waypoints (tee, landing zones, green), splined surface outlines, stamped bunkers with a handful of parameters, an edge-blend width, and 4 pins per hole. Everything else (free sculpting, painting) is polish a small team can skip.
- VGA Golf's "one model, many tee/pin sets" trick is the cheapest multiplier on hole count. Two or three tee boxes times four authored pins gives 8-12 distinct plays per terrain. Mirroring a hole left-right is another free variant, since the solver has no handedness, but spin and wind would flip with it.
- The "auto-generated courses are badly designed" verdict on 2K21 suggests that unconstrained generation is not shippable as-is. The generator should only produce a starting point (or seeded micro-variation inside authored rules) that a validator and a human pass check.

- The crogine `course_format.md` (full field list of `.hole`) was not found on the web. Only the devlog summaries were available.
- No public course-editor documentation was found for other designer-equipped golf games (for example mobile golf games); none came up in searches.

## How to describe a hole as shapes and splines and rasterise it to height and surface grids (edges, smoothing, green contours)?

### Takeaway
Represent each hole as a small parametric spec: a centre-line polyline or spline with a per-station width and elevation profile, a green as a parametric shape plus a few slope primitives, stamped bunkers and water polygons, tee boxes and pin candidates. Rasterise it with signed-distance tests per cell in a fixed priority order. Heights come from a sum of smooth primitives blended by distance-based smoothstep, followed by constrained smoothing and re-flattening of greens and tees. This matches how 2K (splines, stamps, edge blend) and Frostbite (masks plus height overlays) structure surfaces.

### Cited Findings
- Surfaces as splines or brushed shapes, stamped bunkers with depth, lip depth, lip start and lip steepness, and an edge-blending control between surfaces — [PGA TOUR 2K25 Course Designer](https://pgatour.2k.com/2k25/up-your-game/course-designer/); [Game Rant 2K21 guide](https://gamerant.com/pga-2k21-design-course-guide/)
- Terrain as a heightfield plus material masks, with heightfield data deciding mask transitions and noise layers adding variation — [EA/Frostbite](https://www.ea.com/news/procedural-terrain-in-ea-sports-pga-tour)
- Surface type and height baked into one raster at 1 px = 1 m (320 x 200) is enough for a shipped indie golf game — [VGA Golf part 2](https://fallahn.itch.io/vga-golf/devlog/349502/creating-your-own-courses-part-2)
- Green slope limits for pin areas: about 3% is the long-standing ceiling. Current design often keeps cup areas at 2% or less. One combined-reading method keeps downhill plus cross slope under about 5.5% (5% on the front half). At Stimp 14 the recommended limit is about 2.9% (marginal about 3.85%, after architect Jerry Lemons). At Stimp 12 a ball may start rolling on about 5.9% — [search summary of Golf Course Industry / Golf Digest / golfclubatlas sources](https://www.golfcourseindustry.com/article/design-concepts--modern-green-contours); [Golf Course Industry: The fine line of fair competition](https://www.golfcourseindustry.com/news/the-fine-line-of-fair-competition); [Golf Digest: green speeds Pinehurst 2024](https://www.golfdigest.com/story/How-fast-are-the-greens-2024-us-open-pinehurst) (the primary Golf Course Industry "green slopes" article returned an empty page when fetched, so these figures come through search summaries)
- Fairway widths: USGA slope-rating charts imply scratch players need about **32 yd (29 m)** and 20-handicappers about **40 yd (37 m)** to hit fairways regularly. Typical range is 25-65 yd, with "medium" 35-45 yd. Tour guidance is 25-30 yd in landing areas. Strategic left/right choices need 25-50% more (40-48 yd). Brauer argues for varying prime-landing-zone width from 25 to 55 yd between holes. One routing guide sets a 30 yd fairway minimum and 65 yd corridors between trees, water or native areas — [Golf Course Industry: debating fairway widths](https://www.golfcourseindustry.com/article/design-concepts-debating-fairway-widths); [Golf Course Industry: good routing](https://www.golfcourseindustry.com/article/golf-design-good-routing); [Pitchcare: fairways](https://www.pitchcare.com/blogs/news/the-anatomy-of-a-golf-course-fairways) (figures as summarised by search; individual attributions per article not verified line by line)
- Recommended small greens in an indie game: radius about 5-6 m — [VGA Golf part 1](https://fallahn.itch.io/vga-golf/devlog/349460/creating-your-own-courses-part-1). Real greens average about 510 m² (repo report, citing [USGA](https://www.usga.org/content/usga/home-page/articles/2022/06/brookline-small-greens-maintain-play.html)).

### Inferences (proposed concrete design; my synthesis, not sourced)
**HoleSpec (authoring Resource, a few kB per hole)**
```
HoleSpec (Resource, @tool)
  id, course_id, theme, seed:int, par_override:int (0 = auto)
  cell := 0.5            # metres, matches HoleData
  route: PackedVector2Array      # centre-line control points (x,z), tee -> green, 3-6 points
  stations: Array[Station]       # along-route keys, s in metres from tee
     Station { s, half_w_left, half_w_right, elev, cross_slope }   # linear/cubic interp
  tees: Array[TeeBox] { pos:Vector2, yaw, size:Vector2, elev_offset }   # 2-3 boxes
  green: GreenSpec { centre, radii:Vector2, squareness(superellipse n 2..4), yaw,
                     base_tilt:Vector2 (% grade), tiers:Array[Tier], bumps:Array[Bump],
                     cup_zones:Array[Vector2] (optional; auto if empty), fringe_w := 1.0 }
     Tier { line_point, line_dir, rise_m, ramp_w }    # step across a line, smoothstep ramp
     Bump { pos, sigma_m, amp_m }                      # gaussian
  bunkers: Array[Stamp] { shape:PackedVector2Array or (centre,radii,yaw,n), depth, lip_h, lip_w, face_dir }
  water:   Array[PackedVector2Array]   # polygons; level = min ground height inside - 0.3
  mounds:  Array[Bump]
  paths:   Array[PackedVector2Array]   # cart paths (PATH surface), cosmetic
  bounds:  Rect2 or polygon (outside = OUT)
  scatter: Array[ScatterZone] { polygon or band(s0,s1,offset), kind, density_per_100m2, min_spacing }
```
Store as `.tres` while authoring (diffable, AI-editable) and bake to binary `.res` HoleData for shipping (see the Godot section).

**Rasterisation (per cell centre, deterministic, no RNG except seeded noise)**
1. Project the cell onto the route polyline to get station `s` and signed lateral offset `d`. Interpolate the station profile at `s`. Precompute segment lengths once.
2. Signed distances: `sd_fair = |d| - half_w(s, side) + edge_noise(s, side)`, where `edge_noise` is seeded 1D value noise with amplitude about 1-2 m and wavelength about 15-25 m, so fairway edges are organic but reproducible. Green: superellipse SDF in the green's local frame. Bunkers and water: polygon SDF (point-in-polygon plus distance to edges). Tees: rectangle SDF.
3. Surface by priority (later wins): OUT (outside bounds) -> ROUGH (inside the corridor, `|d| < half_w + rough_w`, otherwise OUT or scrub) -> FAIRWAY (`sd_fair < 0`) -> PATH -> FRINGE (`0 <= sd_green < fringe_w`) -> GREEN (`sd_green < 0`) -> TEE -> SAND (`sd_bunker < 0`) -> WATER. Fixed priority makes overlaps well-defined, so an AI-written spec can't create ambiguous cells.
4. Height = `elev(s) + cross_slope(s)*d + terrain_noise(x,z)*w_noise + Σ mounds`. Noise is low-frequency (wavelength 40-80 m, amplitude 0.5-1.5 m), and its weight fades to about 30% inside fairway landing zones.
5. Feature blends via `smoothstep` on SDF: the green surface `g(x,z) = green_base + tilt·p + Σ tiers + Σ bumps` replaces terrain with weight `1 - smoothstep(0, apron_w, sd_green)` (apron about 3-5 m). Tees are flat pads at a fixed height, blended over 2 m. Bunkers: `h -= depth * (1 - smoothstep(-lip_w, 0, sd_bunker))`, plus a lip raise on the face side. Water: clamp `h <= level - 0.3` inside the polygon, and slope banks over 1-2 m.
6. Smoothing: 2-4 passes of a 3x3 Laplacian blur on cells that are not GREEN or TEE (masked), then re-apply the exact green and tee functions. This removes rasterisation stair-steps at 0.5 m cells without touching designed putting surfaces.
7. Write tee, pin (chosen from cup zones by seed via `core/Rng.gd`) and par into HoleData.

**Green contour recipe** (fits the solver's numbers from the repo report: rolling resistance at Stimp 10 holds a ball at rest up to about 7.9%, and shedding ramps need more than about 9%): base tilt 1.5-2.5% back-to-front. Zero or one tier: rise 0.3-0.6 m over a 3-5 m ramp (9-15%). Two to four Gaussian bumps or hollows with sigma 3-6 m and amplitude 0.08-0.25 m. Then auto-detect cup zones: green cells at least 3 m inside the edge where the max gradient within 1.5 m is ≤3% (≤2% for an "easy" pin). Reject the green if fewer than 4 disjoint cup zones exist (mirrors 2K's 4 pins per hole).

**Width defaults scaled to this game:** its casual club ladder (driver about 175 m carry) is shorter than real golf. Landing-zone fairway width of 25-35 m for par 4/5 tee shots, 18-25 m for "tight" strategic holes, never under about 15 m where a driver lands. Vary width between holes rather than inside one hole (Brauer).

### Gaps
- No published spline-to-heightfield algorithm specific to golf was found. The rasterisation above is a standard SDF/composition approach, not a cited golf-industry method.
- No primary source was found for how 2K's "edge blending" is computed (width in metres, curve shape).

## Procedural generation of holes: approaches, constraints, seeded variation, playability, auto par and difficulty

### Takeaway
Little is published specifically on golf-hole generation. The proven pieces are seeded generation with repair (guarantee a fairway path through hazards), constraint and search approaches for routing, and Monte Carlo "simulated golfer" expected-strokes maps for difficulty. For 36+ holes, the efficient approach is a hybrid: a parametric generator proposes HoleSpecs from archetypes (par, length, dogleg, hazard template, theme, seed). A Monte Carlo validator built on the real solver rejects or scores them. A human (or the AI assistant) edits the spec. Runtime seeds vary only pins, tees and wind.

### Cited Findings
- Seeded generation plus repair: seed from hole number, widen a carved path, add hazards, then force a fairway path back through water so the hole is always completable — [ModDB: MiniGolf Endless MMO](https://www.moddb.com/games/minigolf-endless-mmo) (via search summary)
- Shareable seeds for generated holes were planned in an indie procedural mini golf (SereniTee). Grow in the Hole offers fixed daily generated courses playable for one day — [SereniTee devlog](https://dlynch.itch.io/serenitee/devlog/34832/finally-got-around-to-making-the-itchio-page); [search summary of Grow in the Hole](https://www.mobygames.com/game/199790/grow-in-the-hole/)
- Routing as constraint satisfaction (regulations, safety spacing, diversity). Exact CP does not scale, and random search and genetic search were tested as alternatives — [TU Delft thesis, Morssink 2022](https://repository.tudelft.nl/record/uuid:4007f5ae-cd6e-45a5-9cbc-e5d50e82ef35)
- **Simulated-golfer evaluation (Golf Course Wiki model):** a bivariate dispersion PDF per shot. **50 shots per grid point (fast) or 200 (high-res).** Frame-by-frame rollout with gravity and friction. A uniform "5 HCP" golfer. It computes **expected strokes-to-hole from every grid point** and compares with an idealised flat-fairway hole (a "Schoolfield map" = actual minus ideal) to locate penalties. Grid **2 yd x 2 yd takes a couple of minutes; 1 ft x 1 ft takes more than an hour.** Example penalties for the 5 HCP: water about 1 stroke, greenside bunker about 0.5, centre-line bunker about 0.2, the band at 3-wood/4-iron distance about 0.15. Putting uses public strokes-gained data — [Golf Course Wiki: model that visualizes strategic golf](https://golfcoursewiki.substack.com/p/i-spent-the-last-month-and-a-half)
- Par by yardage (USGA, pre-WHS, men/women): par 3 up to 250/210 yd, par 4 251-470/211-400, par 5 471-690/401-575 — [Golfmagic](https://www.golfmagic.com/node/105491). Post-2020 figures quoted by Golf Compendium (par 3 ≤260/220, par 4 240-490/200-420, par 5 450-710/370-600) overlap on purpose. The par-3 number is corroborated by [Maine Golf](https://www.mainegolf.org/clubs/club-services/world-handicap-system/importance-and-determination-of-par/), but the par 4/5 numbers were not verified against a USGA primary source — [Golf Compendium par 4](https://golfcompendium.com/2021/12/par-4-hole-golf.html)
- Par uses **effective playing length**: yardage adjusted for roll, elevation change, dogleg or forced lay-up, prevailing wind and altitude. A hole in an overlap range can be par 4 or 5 depending on difficulty — [USGA Position Paper on Par](https://www.usga.org/content/dam/usga/pdf/USGA-Position-Paper-on-Par.pdf); [USGA Rules of Handicapping Appendix F](https://www.usga.org/handicapping/roh/content/rules/Appendix%20F%20Establishing%20Par.htm)
- Game rule of thumb: par = minimum strokes to the green + 2 — [VGA Golf part 2](https://fallahn.itch.io/vga-golf/devlog/349502/creating-your-own-courses-part-2)

### Inferences (proposed generator; synthesis)
- **Archetype-driven generator, not free noise.** Inputs: `par`, `target_len_m` from the club ladder (repo report: par 3 75-145 m, par 4 230-300 m, par 5 360-400 m), `dogleg {none, L, R, double}` with angle 15-45°, `hazard_template` (for example "carry over water", "fairway bunker at driver landing, inside the dogleg", "pot bunkers short-right", "island green", "two-route split fairway"), `width_class`, `green_template` (tilted, two-tier, punchbowl, crowned), theme and seed. Each template is a small function placing stamps **relative to landing zones** (station = driver carry ±10 m, layup station), not at absolute coordinates. Archetypes keep the result strategic. Pure noise is what produced 2K21's "badly designed" auto courses.
- **Pipeline per candidate:** generate HoleSpec -> bake HoleData (about 0.1-1 s in GDScript; unmeasured) -> cheap structural checks (below) -> Monte Carlo expected strokes with the real solver for 2-3 golfer tiers (reuse the CPU planner's dispersion tiers anchored to Broadie, per the repo report) -> accept if metrics fall in the target band. Otherwise reseed (try N ≤ 50 seeds), or repair (widen the fairway at the failing station, move a bunker 5 m off line, lower a carry).
- **Auto par:** `par = clamp(round(ES_scratchTier_from_tee), length_range(par))`, falling back to "min strokes to green for the mid tier + 2" (the VGA rule). Treat length bands as effective length: add about 1 m per 1 m of uphill elevation as a starting heuristic (unsourced), and add dogleg path length rather than straight-line distance.
- **Difficulty score:** `D = ES_midTier - par` (stroke average over par), plus `P_disaster` = probability of a penalty or ≥ triple bogey for the low tier. Course balance: order holes so a penal hole (D high, P_disaster high) is followed by an easy one, as the repo report recommends. Target per-course mean D within ±0.1 between same-tier courses, so themed courses feel equally fair.
- **Seeded runtime variation (safe):** pick tee box, pin from validated cup zones and wind from `core/Rng.gd`. Never regenerate geometry at runtime. The validator must pass for **every** tee × pin × wind-bucket combination, which is a finite set (for example 3 × 4 × 3 = 36 runs per hole).
- **Throughput to reach 36+ holes:** 4 themed courses × 9 holes. Each course gets 2-3 hand-tuned "signature" holes (the island green, the split fairway) authored as specs directly, and 6-7 generated-then-edited holes. Add tee and pin multiplicity, plus optional mirrored variants for a "reverse" course mode. The AI assistant is well suited to writing HoleSpec `.tres` data and new hazard templates, because both are text and testable.

### Gaps
- No peer-reviewed paper on single-hole golf generation with playability guarantees was found. Generator approaches in shipped games (2K, the itch.io procedural golf titles) are undocumented.
- The Golf Course Wiki article does not describe its aiming algorithm, only expected-strokes maps.
- No source gives a validated formula for elevation-adjusted "plays-like" length for par assignment. The USGA papers list the factors but not the coefficients.

## Godot 4 specifics: terrain meshes from a height grid, surface textures, MultiMesh scatter, Path3D/Curve3D, Resources vs JSON, @tool/EditorPlugin, bake time and memory

### Takeaway
Bake offline in the editor with a `@tool` EditorScript or a small EditorPlugin. Write HoleData as a binary Resource, and at load build the render mesh in chunks directly from the grid with ArrayMesh/SurfaceTool. One terrain shader samples a small surface-ID texture (the same bytes the solver reads). Scatter trees with one MultiMesh per area chunk and a deterministic seed, because MultiMesh culling is all-or-none. Terrain plugins (Terrain3D clipmaps, LiteTerrain) are unnecessary, because the physics already defines the grid and render triangles must match it.

### Cited Findings
- `SurfaceTool.generate_normals()` must be called after adding geometry and before `commit()`. It only works with `PRIMITIVE_TRIANGLES`, and normals are per-face unless smooth groups are used. `generate_tangents()` needs UVs and normals. `SurfaceTool.generate_lod` is **deprecated** (it doesn't preserve normals or UVs); use `ImporterMesh.generate_lods` instead — [Godot docs: SurfaceTool class](https://docs.godotengine.org/en/4.2/classes/class_surfacetool.html); [Godot docs: Using the SurfaceTool](https://docs.godotengine.org/en/4.2/tutorials/3d/procedural_geometry/surfacetool.html)
- MultiMesh draws thousands of copies of one mesh in one call. **Culling is per whole MultiMesh** ("all-or-none"), and the suggested workaround is splitting by area. Allocate `instance_count` at the maximum and drive `visible_instance_count`. Set `transform_format` before `instance_count`. `INSTANCE_ID` and `INSTANCE_CUSTOM` are available in shaders. GDScript is adequate for a few thousand instances. `RenderingServer.multimesh_set_buffer()` sets all instances at once — [Godot docs: Optimization using MultiMeshes](https://docs.godotengine.org/en/stable/tutorials/performance/using_multimesh.html) (the page notes it has not been updated for 4.7)
- Godot 3D optimisation docs list two LOD approaches: automatic mesh LOD on import, and manual **visibility ranges (HLOD)** on nodes — [Godot docs: Optimizing 3D performance](https://docs.godotengine.org/en/4.7/tutorials/performance/optimizing_3d_performance.html)
- A community scatter addon (godot-multimesh-scatter) offers a "chunks" option that splits one scatter node into several MultiMeshes — [mournguard/godot-multimesh-scatter](https://github.com/mournguard/godot-multimesh-scatter); [arcaneenergy/godot-multimesh-scatter](https://github.com/arcaneenergy/godot-multimesh-scatter)
- Forum opinion (not authoritative): about 16k terrain faces is "basically nothing" even on mobile. The likelier cost is the splat-mapping terrain shader, and LOD "is essential" — [Godot Forum: Optimising performance with terrain](https://forum.godotengine.org/t/optimising-performance-with-terrain/19635)
- Terrain3D is a Godot 4 terrain using a geometric clipmap. LiteTerrain is a mobile-oriented terrain addon — [Terrain3D](https://github.com/TokisanGames/Terrain3D); [Godot Asset Library: LiteTerrain](https://godotengine.org/asset-library/asset/5316)
- `@tool` runs a script in the editor. `Engine.is_editor_hint()` gates editor-only code. **Every script a tool script uses must also be `@tool`** (except static methods, constants and enums). Static variables read from non-tool scripts return `null`. Setters don't fire when a sub-resource's properties change; the resource must be `@tool` and emit `changed`. `EditorScript._run()` runs via File > Run / Ctrl+Shift+X. Tool and EditorScript changes have **no undo/redo** and don't mark the scene unsaved (`EditorInterface.mark_scene_as_unsaved()`, `EditorUndoRedoManager`). Nodes added with `add_child()` aren't saved unless `owner` is set. Known bug GH-66381 may require restarting the editor — [Godot docs: Running code in the editor](https://docs.godotengine.org/en/stable/tutorials/plugins/running_code_in_the_editor.html)
- Repo report: a 60 × 320 m corridor at 1 m cells is about 19k samples, about 77 kB. MultiMesh trees take 2-6 draw calls per hole. Working budget is about 100 draw calls and 150-250k triangles (unsourced targets) — `docs/research/Fairway Flick golf game design.md`

### Inferences (proposed Godot implementation; synthesis)
- **Pure logic stays pure.** `HoleSpec` (authoring data) and `HoleBaker.bake(spec) -> HoleData` live in `games/golf/logic/`, with no Node dependency. That keeps them unit-testable headless (CLAUDE.md rule). Because `@tool` scripts can only call `@tool` scripts (static methods excepted), make `HoleBaker` a class of **static functions**, or mark the logic classes `@tool`. Static functions are the cleaner fit and avoid the "static vars return null" trap.
- **Authoring UX, cheapest first:** (1) Hand- or AI-written `HoleSpec.tres` plus an `EditorScript` "Bake all holes" that writes `games/golf/data/holes/<course>/<n>.res` and a PNG preview. (2) A `@tool` `HolePreview` node that rebakes on the spec's `changed` signal and draws the grid as a mesh in the editor viewport. (3) Only if needed: an EditorPlugin with gizmos for dragging route points, tees and pins. `Path3D/Curve3D` is a usable gizmo for the route (built-in handle editing), but store the result as a 2D `PackedVector2Array` in the spec, so the baker does not depend on nodes. Use version control as the undo, since tool edits have none.
- **Storage format:** HoleSpec as text `.tres` (diffable, mergeable, easy for the AI to write and review). Baked HoleData as binary `.res`, or a raw `PackedByteArray` file, loaded once per hole. JSON is fine for the spec but loses typed `PackedVector2Array` and `Resource` references, and Godot's JSON parses all numbers as float. Prefer `.tres` for specs. Keep a CI test that rebakes every spec and compares a hash of the HoleData, which guards determinism and catches stale bakes. (Godot behaviour around `.tres`/`.res` via `ResourceSaver` is standard; the relevant doc pages were not fetched in this session.)
- **Memory per hole (computed):** a par 4 corridor of 80 × 320 m at 0.5 m cells = 160 × 640 cells → 103,201 float heights = **413 kB** plus 102 kB surface bytes, about 0.5 MB. At 1 m cells: about 104 kB plus 26 kB. A par 5 at 400 m and 0.5 m is about 0.65 MB. Only one hole needs to be resident (SceneRouter loads one game). Shipping 36 holes at 0.5 m is about 18-25 MB uncompressed in the pack. Options: bake at 1 m away from greens and keep 0.5 m only on greens by using two HoleData layers (needs a solver change), or quantise heights to uint16 at 1 cm (half the size, still deterministic if dequantised identically everywhere).
- **Render mesh (computed):** 160 × 640 cells = 204,800 triangles if rendered 1:1. That is the whole triangle budget. Mitigations: (a) the render mesh only has to match the solver **where the ball can be seen up close**, so build chunks of 32 × 32 cells (2,048 triangles each, 100 chunks). Render full-res chunks near the camera and the green, and 2× or 4× decimated chunks for far ones, switched with `visibility_range_begin/end` (HLOD), which the docs list as the manual LOD method. (b) Skip chunks that are fully OUT and covered by trees or backdrop. (c) Flat-shaded fairways look fine, but smooth normals should be computed from the grid analytically (central differences), not via `generate_normals`, so seams between chunks match. Build with `ArrayMesh.add_surface_from_arrays` from `PackedVector3Array` and `PackedInt32Array` (one index buffer reused by every full-res chunk). Each chunk also takes the same (i,j)->(i+1,j+1) diagonal as HoleData.
- **Surface texture:** upload `HoleData.surface` directly as an `Image.FORMAT_R8` texture (nx × nz; 160 × 640 = 100 kB), sampled with `texelFetch` (nearest) for the ID, plus a second blurred copy, or a few-tap filter in the shader, for soft edges. Fringe, stripes and grass detail come from shader maths (the repo report already plans this). What the player sees is exactly what the solver reads, which matters for fairness.
- **Deterministic scatter:** at bake time, generate tree, rock and bush positions with Poisson-disk or jittered-grid sampling seeded from `hash(hole_id, zone_index)` via `core/Rng.gd`. Accept only on allowed surfaces (ROUGH/OUT, at least X m from fairway and green edges, never within the validated landing corridors). Store the transforms in HoleData (or a sibling `HoleScatter` resource) so the solver's analytic tree cylinders and the rendered trees come from the same list. Render with one MultiMesh per (mesh kind × area chunk of about 64 × 64 m), so the all-or-none culling still culls behind the camera. A hole with 200-600 trees in 3 species and 8 chunks stays within about 10-25 draw calls (estimate). Use a crossed-quad or low-poly impostor mesh plus `visibility_range` LODs.
- **Bake time:** unmeasured. A GDScript loop doing about 10-20 SDF and noise evaluations per cell over about 100k cells is likely in the low seconds on desktop (estimate). That is fine for an offline editor bake, and another reason **not** to bake on the phone at runtime. Measure it with a benchmark test and record it in docs/PROGRESS.md.

### Gaps
- No measured numbers were found for GDScript heightfield bake time, or for chunked ArrayMesh terrain frame times on mid-range Android in Godot 4.7. Both need an in-repo benchmark.
- The Godot `Resource`/`ResourceSaver`, `EditorPlugin` and `Path3D` doc pages were not fetched in this session, so claims about them above are standard engine knowledge rather than cited.

## Validation and testing: automated per-hole checks and tuning with simulated golfers

### Takeaway
Treat every hole (× tee × pin × wind bucket) as a test case in gdUnit4. Run fast geometric checks on the baked grid (widths, green slopes, traps, bounds), then Monte Carlo playability with the real deterministic solver and the CPU's dispersion tiers (expected strokes, penalty rate, can-reach-green, no-dead-ends). Tune by comparing expected-strokes and penalty maps against targets, the way the Golf Course Wiki model does, then confirm with phone playtests.

### Cited Findings
- Expected-strokes-from-every-point maps (50-200 simulated shots per point, dispersion PDF, rollout physics) reveal where hazards cost strokes and by how much (water about 1.0, greenside bunker about 0.5, centre-line bunker about 0.2 for a 5 HCP). Maps are skill-specific, and grid resolution drives cost (2 yd grid: minutes; 1 ft grid: more than an hour) — [Golf Course Wiki](https://golfcoursewiki.substack.com/p/i-spent-the-last-month-and-a-half)
- Shipped designer guidance is to playtest for unplayable areas and spots much harder than the rest of the course. Pins are limited to 4 per hole — [PGA TOUR 2K25 Course Designer](https://pgatour.2k.com/2k25/up-your-game/course-designer/)
- Random hazards made procedurally generated holes uncompletable until a guaranteed path was added — [ModDB: MiniGolf Endless MMO](https://www.moddb.com/games/minigolf-endless-mmo)
- Pin-area slope limits (≤3%, modern ≤2%, combined ≤5.5%) and fairway width benchmarks (29-37 m for scratch to 20 HCP) — see the sources in the rasterisation section above.
- Repo context: the CPU planner already runs Monte Carlo over the real solver (about 100 rollouts in 0.4 s on the test phone), with Broadie-anchored dispersion tiers — `docs/research/Fairway Flick golf game design.md`

### Inferences (proposed test suite; thresholds are starting values to tune)
**Structural checks (milliseconds per hole, run on every spec in `tests/`):**
1. Bake determinism: `hash(HoleData)` equals the stored golden hash. Rebake twice gives the same result.
2. Surface sanity: tee pads are TEE, flat (max gradient ≤1%) and at least 4 × 3 m. The pin cell is GREEN. A FRINGE ring fully surrounds GREEN (no GREEN-ROUGH adjacency unless flagged). No GREEN touches WATER without a fringe or bank. Every SAND cell sits lower than its neighbours' rim (catch-basin), but has an exit gradient ≤ about 25% on at least one side (no unplayable pits).
3. Landing zone width: for each tee and each landing station (each club in the ladder that a tier would hit from that tee, ±10 m along route), measure the contiguous FAIRWAY width perpendicular to the route. It must be at least `w_min(tier, club)`: about 15 m for driver on "tight", 22-30 m default; the green must be at least 18 m across for wedge approaches.
4. Green and cup checks: at every pin candidate, max gradient within 1.5 m is ≤3% (≤2% on Easy), and the pin is at least 3 m from the green edge. There must be at least 4 distinct pins per hole. Ramps meant to shed balls must be more than 9%. No green cell may exceed 8% (the at-rest threshold is about 7.9% at Stimp 10), unless it's tagged as a shedding ramp.
5. No ball traps: flood-fill "rest basins". Any local minimum region outside GREEN, SAND or WATER that's smaller than about 2 m and deeper than about 0.3 m is flagged. So is any reachable cell from which no club in the ladder can produce a shot that leaves the region (computed by Monte Carlo on flagged cells only).
6. Bounds and corridor: OUT is at least 10 m from fairway centre at every station. The hole fits its declared grid with a margin of at least 20 m behind the green. Water polygons carry a declared drop zone that is FAIRWAY or ROUGH and lies on the tee side.
7. Forced-carry rule: every forced carry over WATER or OUT from a tee must be ≤ the low tier's reliable 80th-percentile carry for some club, or have a bail-out route (a FAIRWAY path around it) — an extension of the repo report's validator rule.

**Monte Carlo playability (seconds per hole; run in CI, maybe tagged "slow"):**
- For each tier (Easy/Normal/Hard CPU dispersion) × tee × pin × wind bucket: play N = 64-200 full holes with the CPU planner over the real solver, seeded by test index through `core/Rng.gd`. Assert: P(hole out within par + 3) = 1.0 for all tiers (with the triple-bogey pick-up rule); P(green reached in regulation) for the Normal tier inside a target band (for example 35-70%); stroke average minus par inside a tier band (for example Hard tier -0.3 to +0.3, Easy tier +0.5 to +1.5); P(penalty) for the Easy tier ≤ about 25% unless the hole is tagged "heroic".
- Expected-strokes heatmap (Golf Course Wiki style) at 4 m grid resolution, written as a PNG to `user://` for a human to inspect, with the "Schoolfield" penalty map (actual minus ideal flat hole) to check hazards cost what the design intends (for example a greenside bunker about +0.3 to +0.6).
- Course-level: total par equals the declared value, difficulty ordering alternates (no two holes with D in the top quartile back to back), and per-course mean D is within ±0.15 across themed courses.

**Tuning loop:** generate or edit spec -> bake -> structural tests -> MC metrics plus heatmap -> adjust spec parameters (width, bunker offset, green tilt) or the generator's template constants -> record per-hole metrics in a CSV (similar to the existing `physics-tune` skill's CSV workflow) -> phone playtest the hole with `--game=golf --hole=<id>` and capture a screenshot per CLAUDE.md.

### Gaps
- No published set of automated playability thresholds for golf video-game holes was found. The numbers above are design starting points derived from real-course guidance and the repo's solver figures, not cited standards.
- Real-world amateur fairway-hit and GIR rates by handicap (to anchor the target bands) were not researched here. Broadie's data, already cited in the repo report, is the natural source.
