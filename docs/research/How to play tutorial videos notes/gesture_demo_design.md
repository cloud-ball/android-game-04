# Visual and Motion Design of Animated Gesture Demos ("ghost hand") and Tutorial Cards for Mobile Games

Context assumed throughout: Pocket Arena 8, Godot 4.7, portrait 1080 px wide canvas. On a 420 dp wide phone, 1 dp is about 2.57 canvas px, so 8 dp is about 21 px, 36 dp is about 93 px and 48 dp is about 123 px. These conversions are my own arithmetic, not sourced.

## 1. Depicting touch gestures clearly (glyph choice, tap ripple, press/hold, swipe trails, flick vs drag, two-finger tap, timings)

### Takeaway
No study compares a hand glyph with an abstract touch dot. Practitioner notation pairs the two: a simplified hand for orientation and context, a dot for the contact point, a ringed dot for press/hold, and arrows or trails for direction. Android's own constants give defensible timings to build demos on: 100 ms tap timeout, 400 ms long-press, 300 ms double-tap window, 8 dp touch slop, ripple 75 ms fade-in / 225 ms expand / 150 ms fade-out. A flick should read as fast (short time, motion blur or streak), and a drag should read as slow and stepwise (the finger pauses at each column).

### Cited Findings
**Notation conventions (hand vs dot)**
- Steven Hoober's touch/gesture design language (2019) uses a simplified line-drawn hand, not a photo, as "the key orienting element". Fingers are drawn opaque so they visibly take up space on the layout. A plain dot marks a single touch, a ring around the dot marks press or touch-and-hold, and arrows show direction for drag, scroll and rotate. A separate line plots speed over time, and time is "rarely drawn to scale because the most critical phases can be very short." — [UXmatters, Hoober 2019](https://www.uxmatters.com/mt/archives/2019/05/a-design-language-for-touch-gesture-and-motion.php)
- Hoober also uses a small coloured dot under the fingertip to show the interaction itself, separate from where the finger lands. — [UXmatters, Hoober 2019](https://www.uxmatters.com/mt/archives/2019/05/a-design-language-for-touch-gesture-and-motion.php)
- That article does not cover fling or multi-finger notation, and gives no sizes. — [UXmatters, Hoober 2019](https://www.uxmatters.com/mt/archives/2019/05/a-design-language-for-touch-gesture-and-motion.php)
- I found no usability study directly comparing a hand glyph with a touch dot. Search results contained only asset packs and practitioner opinion. — [UXmatters "Designing for Touch" 2020](https://www.uxmatters.com/mt/archives/2020/02/designing-for-touch.php); [Designmodo gesture icons](https://designmodo.com/gesture-icons/)
- Material Design (M2 gestures page, summarised by search) advises that where there are no other affordances, icons can show that a gesture is possible. It also says to animate elements before the user interacts with them to suggest a gesture, and that during a gesture elements should move in a way that shows the gesture's purpose. — [Material Design: Gestures](https://m2.material.io/design/interaction/gestures.html) (page is JS-rendered; content came via search summary, not a direct read)
- Apple's WWDC21 "Discoverable design" session notes that gestures "are invisible, and so might not be as immediately discoverable", and recommends using animation to reveal them. — [Apple WWDC21 10126](https://developer.apple.com/videos/play/wwdc2021/10126/)

**Android touch-feedback ripple (reference timings for a tap pulse)**
- Jetpack Compose ripple constants: `FadeInDuration = 75` ms, `RadiusDuration = 225` ms (also used for moving the ripple centre), `FadeOutDuration = 150` ms. Start radius is `max(width, height) * 0.3f`. The doc comment says 60%, but the code uses 0.3. — [AOSP RippleAnimation.kt](https://android.googlesource.com/platform/frameworks/support/+/androidx-main/compose/material/material-ripple/src/commonMain/kotlin/androidx/compose/material/ripple/RippleAnimation.kt)

**Android gesture thresholds (useful for making demo motion match what the game will accept)**
- AOSP `ViewConfiguration` defaults: TAP_TIMEOUT 100 ms, DEFAULT_LONG_PRESS_TIMEOUT 400 ms, DOUBLE_TAP_TIMEOUT 300 ms, DOUBLE_TAP_MIN_TIME 40 ms, PRESSED_STATE_DURATION 64 ms, TOUCH_SLOP 8 dp, PAGING_TOUCH_SLOP 16 dp, DOUBLE_TAP_SLOP 100 dp, MINIMUM_FLING_VELOCITY 50 dp/s, MAXIMUM_FLING_VELOCITY 8000 dp/s, MULTI_PRESS_TIMEOUT 300 ms. The Context-based constructor replaces slop and fling values with device resource values. — [AOSP ViewConfiguration.java](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/core/java/android/view/ViewConfiguration.java)
- Official API definitions: the tap timeout is "the duration in milliseconds we will wait to see if a touch event is a tap or a scroll". The long-press timeout is "the duration in milliseconds before a press turns into a long press". Touch slop is the "distance in pixels a touch can wander before we think the user is scrolling". — [Android ViewConfiguration reference](https://developer.android.com/reference/android/view/ViewConfiguration)

**Android's own gesture-navigation education**
- The Pixel/AOSP gesture-navigation tutorial is an interactive "sandbox". It recognises the user's real back gesture to step through right-edge and left-edge steps, and uses fake task-view animations driven by the gesture (a shared `SwipeUpGestureTutorialController`) with spring-based home animations. — [Launcher3 commit (OmniROM mirror)](https://gerrit.omnirom.org/plugins/gitiles/android_packages_apps_Launcher3/+/b55d5b279b3902e57f079afb628d10607bd42ac5%5E1..b55d5b279b3902e57f079afb628d10607bd42ac5); [Launcher3 Overview Sandbox commit](https://gerrit.omnirom.org/plugins/gitiles/android_packages_apps_Launcher3/+/fad8a87773393e2033df9cabd0355563cad2536b%5E%21). I could not extract its exact animation durations or hand-glyph visuals from these sources.

### Inferences
- **Glyph:** use a stylised, original fingertip or hand silhouette (line or flat neon outline in the game's purple palette, about 60-70% opacity) that carries a bright contact dot. The hand gives orientation (which way the finger travels). The dot gives precision (where the touch lands) and stays readable when the demo is small. In very small demo areas (under about 200 dp tall), drop the hand and keep the dot plus trail.
- **Tap:** finger descends (anticipation: a small 4-6% scale-down, about 100 ms), then contact. The dot appears, a ring expands from about 0.3x to 1.0x of its final radius over about 225 ms, and the ring fades out over about 150 ms, mirroring the Compose ripple numbers. A final ring diameter of about 48 dp (about 123 canvas px) matches a touch-target scale. The finger lifts about 100 ms after contact, which is consistent with a 100 ms tap timeout.
- **Press/hold:** keep the dot and show a steady ring (Hoober's "ringed dot") that fills around its circumference as a progress arc over about 400 ms (the long-press default), then pulses once on recognition. Stack Drop has no long-press, so do not draw a hold state there. Its absence then visually separates "tap = rotate" from any hold.
- **Swipe (Serpent Grid turn):** the dot moves 60-120 dp with an ease-out curve over about 150-250 ms. It leaves a tapered trail (thick at the head, transparent at the tail) about 40-60% of the stroke length that fades over about 200-300 ms after lift. A chevron at the trail head shows direction. The world reacts on the same beat (the snake turns), so cause and effect are paired, as the Material guidance suggests.
- **Drag (Stack Drop column move):** move slowly and in steps. The finger travels 36 dp per column with a short dwell (about 80-120 ms) at each step, and the piece snaps one column per step in sync. Show tick marks or ghost column outlines at each 36 dp step, and do not use a streak trail. Slow, stepped and tied to the grid reads as "drag".
- **Flick (hard drop):** make it short and fast. About 100-150 ms of travel with ease-in (it accelerates and leaves the touch), a long speed-streak trail plus 2-3 motion-blur ghost copies, then an immediate impact flash on the piece landing. To the eye, the duration ratio (flick about 3-5x faster than one drag step) does the explaining. Above about 50 dp/s counts as a fling to Android by default, so a 120 ms, 80 dp flick (about 670 dp/s) is safely in "fling" territory.
- **Two-finger tap (HOLD alternative):** two contact dots land at the same moment (within about 40 ms of each other, so they read as simultaneous), each with its own ripple. Join them with a faint bracket or a small "x2" badge so the count does not depend on noticing two dots. Show the HOLD button highlight pulsing at the same moment, so both routes to the same action appear in one frame.

### Gaps
- No primary-source numbers for gesture trail length or fade, or for hand-glyph size. These are design judgments.
- The Material M2 gestures page and the Apple HIG pages are JS-rendered and could not be fetched directly. Their content is cited via search summaries only.
- I could not retrieve exact durations from Android's gesture-navigation tutorial animations.

## 2. Motion design principles for tutorial loops (easing, durations, loop pauses, anticipation, small-size legibility, frame rate)

### Takeaway
Use Material 3's tokenised durations (50-1000 ms) and easings: emphasized decelerate `cubic-bezier(0.05, 0.7, 0.1, 1)` for entrances, standard `cubic-bezier(0.2, 0, 0, 1)` for in-screen moves, and accelerate curves for exits. Keep individual UI moves in the 100-500 ms band NN/g recommends. No source gives a standard pause between loop repetitions. The best-supported pattern is a short loop, shown in context, that stops once the user performs the gesture.

### Cited Findings
- M3 easing tokens: Standard `cubic-bezier(0.2, 0, 0, 1)` ("utility focused animations that begin and end on screen"). Standard Decelerate `(0, 0, 0, 1)` (enter). Standard Accelerate `(0.3, 0, 1, 1)` (exit). Emphasized is a two-segment path, `M 0,0 C 0.05,0, 0.133333,0.06, 0.166666,0.4 C 0.208333,0.82, 0.25,1, 1,1`. Emphasized Decelerate `(0.05, 0.7, 0.1, 1)`. Emphasized Accelerate `(0.3, 0, 0.8, 0.15)`. Linear `(0, 0, 1, 1)`. — [Material Components Android: Motion.md](https://github.com/material-components/material-components-android/blob/master/docs/theming/Motion.md)
- M3 duration tokens: Short1-4 = 50/100/150/200 ms. Medium1-4 = 250/300/350/400 ms. Long1-4 = 450/500/550/600 ms. ExtraLong1-4 = 700/800/900/1000 ms. "Duration should increase as the area/traversal of an animation increases." — [Material Components Android: Motion.md](https://github.com/material-components/material-components-android/blob/master/docs/theming/Motion.md)
- NN/g (Laubheimer, 2020): "the duration of most animations should be in the range of 100–500 ms". About 100 ms for small feedback such as toggles. 200-300 ms for larger changes such as modals. 400 ms is "a very slow animation, to be used only for big movements across large screens". Entrances should be slightly longer than exits (for example 300 ms in, 200-250 ms out). Ease-out is the most recommended curve, and linear looks unnatural. "The more frequent the animation, the more subtle and shorter you'll want it to be." — [NN/g: Animation Duration](https://www.nngroup.com/articles/animation-duration/)
- No source gives a recommended interval between repetitions of a looping hint. The best-supported pattern is to keep hints brief, show them in context, and retire them once the user performs the real action (example: a hint "permanently retire[d] after a real transform is used"). — [LightHouse PR #31](https://github.com/udeudeude/LightHouse/pull/31); [Shopify: mobile onboarding](https://www.shopify.com/partners/blog/mobile-app-onboarding)
- A 2025 CHI paper tested temporary visual signifiers in animated transitions to aid swipe discoverability. It notes that "previous work is inconclusive about the importance of temporal placement for interaction signifiers" for single-finger in-place inputs. — [ACM CHI 2025, "Does Adding Visual Signifiers in Animated Transitions Improve Interaction Discoverability?"](https://dl.acm.org/doi/10.1145/3706598.3713914)
- NN/g says interactivity cues should appear immediately and "should not require any interaction cost to dismiss". Its hover-intent timings are about 0.3-0.5 s. — [NN/g: Timing Guidelines for Exposing Hidden Content](https://www.nngroup.com/articles/timing-exposing-content/)
- Android's text-cursor blink interval is constrained to ">= 333 (fast blink, the minimum blink interval that is comfortable for photosensitivity)". This is a platform-sourced floor for any repeating blink or pulse. — [Android ViewConfiguration reference](https://developer.android.com/reference/android/view/ViewConfiguration)

### Inferences
- **Loop structure (suggested, about 2.4-3.2 s per cycle):** (1) hand fades and slides in, about 250-300 ms, emphasized decelerate. (2) Anticipation: the hand settles and presses, about 100-150 ms. (3) Gesture action, 100-600 ms depending on gesture (flick shortest, stepped drag longest). (4) World reaction plus follow-through, about 300-400 ms. (5) Hold the result still, about 500-800 ms, so the outcome can be read. (6) Hand exits, about 200 ms, accelerate. (7) Rest pause, about 600-1000 ms, before repeating. The rest pause keeps the loop from feeling frantic and makes each cycle's start obvious. These numbers combine the M3 tokens and the NN/g ranges; they are not a published standard.
- Keep individual moves inside the 100-500 ms band. The demo's overall slowness should come from holds and pauses, not from slow easing, which looks mushy.
- **Small-size legibility:** one gesture per demo, high-contrast dot (white or yellow core on the purple scene), a ring stroke of at least about 2 dp, and trails at least about 4 dp thick at the head. Simplify the game scene inside the demo (a 6x10 mini-board rather than the full 12x24 well) so the gesture effect is large relative to the frame.
- **Frame rate:** drive the demo with Godot Tweens or an AnimationPlayer in `_process`, at render rate. The demo is not simulation. If it replays the real logic class, use fixed-step seeded input scripts so every loop is identical. Per CLAUDE.md, set `physics_interpolation_mode = OFF` on the demo root because it moves nodes in `_process`.
- **Pulse/blink rates** (for "tap here" pulses): keep the period at or above about 333 ms, and in practice use about 800-1200 ms for calm pulses.

### Gaps
- No empirical source for the ideal pause between loop repetitions, or for how many repetitions to show before stopping.
- No sourced rule for minimum stroke or dot sizes for legibility in small animated demos.

## 3. Tutorial card layout (demo area, captions, step indicators, buttons, swiping, autoplay vs tap-to-advance)

### Takeaway
Research favours very few, very short, visual, skippable and revisitable instructions shown in context, over long walkthrough decks. NN/g finds walkthroughs "dramatically overused" and "frequently skip[ped]". It recommends one focused hint at a time, short text paired with visuals, and keeping help reachable later. Specific layout numbers (aspect ratios, word counts, dot sizes) are not in the authoritative sources and are design judgments.

### Cited Findings
- NN/g (Harley, 2014): show hints one at a time, each focused on one interaction. Avoid chains of tips because they make an app "appear overly complicated and daunting". Keep text "as short as possible" and scannable. Pair images with ultra-short text, and for complex workflows use a single visual intro screen instead of a series of popups. Short-term memory "fades in about 20 seconds". Make hints visually distinct from the real UI so users do not try to tap them. — [NN/g: Instructional Overlays and Coach Marks](https://www.nngroup.com/articles/mobile-instructional-overlay/)
- NN/g (Laubheimer, 2023): tutorials are "dramatically overused", users "frequently skip them" (the "paradox of the active user"), and they are "quickly forgotten". They can help for a "novel interaction paradigm". The article recommends making help dismissible and recoverable (still reachable from a menu later), using brief animations with a "learn more" path (progressive disclosure), and hands-on, revisitable tutorials. It does not address the number of screens or progress indicators. — [NN/g: Onboarding Tutorials vs. Contextual Help](https://www.nngroup.com/articles/onboarding-tutorials/)
- Shopify: show only the primary features in the first-time experience, let users discover secondary features over time, and show hints when the user reaches the relevant section. — [Shopify: Mobile App Onboarding](https://www.shopify.com/partners/blog/mobile-app-onboarding)
- Game-UX blogs (thin sourcing) recommend making tutorials skippable, teaching mechanics in a safe low-risk situation, delivering information "when it's needed, not before", and mixing short clips with interactive challenges so players learn by doing. — [Inworld: game tutorial design](https://inworld.ai/blog/game-ux-best-practices-for-video-game-tutorial-design); [Acagamic newsletter, citing a Celia Hodent interview](https://acagamic.com/newsletter/2023/04/04/dont-spook-the-newbies-unveiling-5-proven-game-onboarding-techniques/) (secondhand)
- Android's own gesture tutorial teaches by having the user perform the gesture in a sandbox that recognises it. — [Launcher3 commit](https://gerrit.omnirom.org/plugins/gitiles/android_packages_apps_Launcher3/+/b55d5b279b3902e57f079afb628d10607bd42ac5%5E1..b55d5b279b3902e57f079afb628d10607bd42ac5)
- Android accessibility guidance specifies touch targets of at least 48x48 dp. — [Android: Make apps more accessible](https://developer.android.com/guide/topics/ui/accessibility/apps)

### Inferences
- **Card count:** about 3-4 cards per game, one gesture per card. Serpent Grid could use Swipe to turn, Edges wrap, Make the CPU crash. Stack Drop could use Tap rotate, Drag move, Flick drop, HOLD plus Clear rows sends garbage. Merge or cut any card that does not teach a non-obvious interaction (NN/g: skip the self-explanatory).
- **Portrait layout on the 1080 canvas:** demo area about 80-88% of width (about 860-950 px). A 4:5 or 1:1 aspect fits portrait without crowding, so about 950x950 to 950x1190 px. Caption below the demo, centred, 1-2 lines, about 3-8 words (for example "Swipe anywhere to turn"), at 40-48 px for the headline and 32-36 px for an optional sub-line. Place the caption near the demo so the eye does not have to move across the screen.
- **Step indicator:** dots under the caption. The active dot is elongated or filled and the others are outlined, so state is not shown by colour alone (see section 4). Dots are not tap targets unless padded to 48 dp.
- **Buttons:** primary "Next" / final "Got it" bottom-right or full-width at the bottom (thumb zone), at least 48 dp tall (about 123 canvas px). "Skip" top-right as a text button. "Back" bottom-left, or rely on swipe-back. Horizontal swipe between cards should also work.
- **Advance mode:** tap-to-advance, or swipe, as the main mode, with the demo looping inside each card. Avoid auto-advancing cards, which would also trigger WCAG 2.2.2 concerns. Better still: on the last card or the first play, let the player do each gesture once in a mini sandbox and tick it off (the Android gesture-tutorial pattern). Keep "How to play" reachable from the pause menu (NN/g: recoverable help).
- **Distinct from live UI:** frame the demo area (rounded panel, subtle vignette, "DEMO" style treatment) so players do not try to play inside the animation (NN/g point about overlays looking interactive).

### Gaps
- No authoritative numeric guidance on caption word limits, demo aspect ratio, number of cards, or dot-indicator sizes. The above are inferences.
- I could not verify Celia Hodent's own published framework (only secondhand coverage), and could not retrieve Apple HIG onboarding text directly.

## 4. Accessibility (reduced motion, pause/stop/hide, contrast, not relying on colour, text sizes)

### Takeaway
Respect Android "Remove animations" by reading `Settings.Global.ANIMATOR_DURATION_SCALE`, where 0 means removed. When it is on, show a static key frame with arrows and the caption, plus a manual step-through. Any demo that loops for more than 5 s alongside other content needs a pause/stop control (WCAG 2.2.2). Captions need at least 4.5:1 contrast at these text sizes, and gesture glyphs at least 3:1. Never encode meaning only in colour.

### Cited Findings
- WCAG 2.2.2 Pause, Stop, Hide (Level A): moving, blinking or scrolling content that (1) starts automatically, (2) lasts more than five seconds, and (3) is presented in parallel with other content needs "a mechanism for the user to pause, stop, or hide it", unless it is essential. Content not presented in parallel with other content is exempt. Sufficient techniques include G4 (pause and restart from where paused) and G152 (stop animated GIFs after n cycles within 5 s). The Understanding doc gives an example animation demonstrating a process that has pause and restart buttons. — [W3C Understanding 2.2.2](https://www.w3.org/WAI/WCAG22/Understanding/pause-stop-hide.html)
- WCAG 2.3.3 Animation from Interactions (Level AAA): "Motion animation triggered by interaction can be disabled, unless the animation is essential". Motion animation is "addition of steps between conditions to create the illusion of movement". Changes of colour or opacity that do not change perceived size, shape or position are not motion animation (an errata note concerns blurring). Techniques: C39 / SCR40 (prefers-reduced-motion) and allowing users to set a preference that prevents animation. — [W3C Understanding 2.3.3](https://www.w3.org/WAI/WCAG22/Understanding/animation-from-interactions.html)
- NN/g: for users who set "reduce motion", animations should be removed. — [NN/g: Animation Duration](https://www.nngroup.com/articles/animation-duration/)
- Android "Remove animations": no dedicated API. Read `Settings.Global.getFloat(contentResolver, Settings.Global.ANIMATOR_DURATION_SCALE)`, where `0f` means removed. Catch `SettingNotFoundException` and default to `1f`. Compose animations follow the setting from 1.2.0, and Lottie shows its first frame. If the first frame is unsuitable, show a purpose-made static image. — [Eevis Panula, dev.to, Dec 2022](https://dev.to/eevajonnapanula/android-animations-and-reduced-motion-2em2)
- The AOSP Settings toggle sets WINDOW_ANIMATION_SCALE, TRANSITION_ANIMATION_SCALE and ANIMATOR_DURATION_SCALE to 0 together (restores to 1 when off). — [AOSP Settings DisableAnimationsPreferenceController (Replicant mirror)](https://git.replicant.us/replicant-next/packages_apps_Settings/plain/src/com/android/settings/accessibility/DisableAnimationsPreferenceController.java)
- Android limits cursor blink to at least 333 ms as "the minimum blink interval that is comfortable for photosensitivity". — [Android ViewConfiguration reference](https://developer.android.com/reference/android/view/ViewConfiguration)
- Known WCAG thresholds, not individually fetched in this session. 1.4.3 Contrast (Minimum, AA): 4.5:1 for normal text, 3:1 for large text (18 pt, or 14 pt bold). 1.4.11 Non-text Contrast: 3:1 for graphical objects needed to understand content. 1.4.1 Use of Color: colour must not be the only visual means of conveying information. 2.3.1 Three Flashes: nothing flashes more than three times in any one-second period. — [W3C Understanding 1.4.3](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html); [1.4.11](https://www.w3.org/WAI/WCAG22/Understanding/non-text-contrast.html); [1.4.1](https://www.w3.org/WAI/WCAG22/Understanding/use-of-color.html); [2.3.1](https://www.w3.org/WAI/WCAG22/Understanding/three-flashes-or-below-threshold.html)

### Inferences
- **Reduced-motion mode:** when the scale is 0, show each card as a static key frame. Draw the hand at the gesture start, with a dashed arrow for swipe, stepped arrows with tick marks for drag, a bold arrow plus a speed-line symbol for flick, and two dots with "x2" for two-finger tap. Optionally add a "Play demo" button for users who choose to see motion, since 2.3.3 allows user-initiated choice. Godot does not expose this setting natively as far as I found. It needs a small Android plugin or JNI call, or an in-game "Reduce motion" toggle in Settings, which the hub should offer anyway (WCAG technique "allow users to set a preference").
- **Pause control:** the demo loops longer than 5 s and sits beside a caption and buttons, so either add a pause/play toggle on the demo (tap the demo to pause, with a visible icon) or stop looping after about 2-3 cycles and show a "Replay" button (the G152 pattern). The second option is simpler and also saves battery and GPU.
- **Text size:** 32-40 px on a 1080 canvas is about 12.4-15.6 dp/sp. Under WCAG that is "normal" text, so captions need at least 4.5:1 against the card background (white or near-white on the dark purple card easily exceeds this). Prefer at least 40 px (about 15.6 sp) for the main caption. Dots, rings and trails need at least 3:1 against the demo background. Neon glow does not count toward contrast, so the solid core colour must pass on its own.
- **Not relying on colour:** distinguish flick from drag by shape and motion (streak plus speed lines vs tick-stepped path), not by trail hue. Show the active step dot by shape or size as well as colour. Give the two-finger state a numeric "x2" badge.
- **Flashing:** impact flashes (hard drop, crash) should stay under 3 per second and avoid large saturated red full-frame flashes.

### Gaps
- No Godot 4.7 built-in API for reading Android's animation scale was found. This needs verification in Godot docs or a plugin.
- The WCAG 1.4.3, 1.4.11, 1.4.1 and 2.3.1 values are well established but were not re-fetched in this session.

## 5. Keeping visuals original (avoid imitating specific products)

### Takeaway
Base every demo glyph and scene on the game's own art (Serpent Grid's neon snake and orbs, Stack Drop's own block style and well), draw a custom hand or fingertip glyph, and follow generic notation conventions (dot, ring, arrow), which are common vocabulary rather than any product's trade dress.

### Cited Findings
- Hoober's notation (dot = touch, ring = press/hold, arrows = direction, simplified hand) is presented as a general-purpose design language, not one product's UI. — [UXmatters, Hoober 2019](https://www.uxmatters.com/mt/archives/2019/05/a-design-language-for-touch-gesture-and-motion.php)
- Material guidance: elements should move in ways that demonstrate the gesture's purpose. Teach with your own content's response, not a generic overlay. — [Material Design: Gestures](https://m2.material.io/design/interaction/gestures.html) (via search summary)
- NN/g: hints should use a visual style distinct from the interactive UI (its example: a different font or a hand-drawn feel). This supports a bespoke hint style. — [NN/g: Instructional Overlays](https://www.nngroup.com/articles/mobile-instructional-overlay/)
- Stock "animated touch gesture" packs exist commercially (realistic and cartoon hands). — [Envato: Real Touch bundle](https://elements.envato.com/real-touch-bundle-2-NBZFQH6); [Envato: Cartoon hand gestures](https://elements.envato.com/cartoon-hand-touch-gestures-on-phone-J9PHNSE)

### Inferences
- Draw an original glyph: for example a rounded neon fingertip capsule with a soft glow, in the hub's purple/cyan palette, rather than a photographic hand or a recognisable stock cartoon hand. Avoid licensed gesture packs, both for stylistic consistency and to avoid licence and "looks like X" issues.
- Render demos in-engine using the real game renderer or logic with scripted inputs, not pre-rendered video. This automatically matches the game's art, stays crisp at any DPI, keeps the APK small, and cannot drift from current rules. Do not port or trace any reference mock or commercial screenshot (per the project rule that docs/refs prototypes are throwaway).
- Run the project's ip-checker agent on caption strings, for example to avoid naming any commercial falling-block or snake title in captions.

### Gaps
- No legal or IP-specific source was researched. The originality guidance above comes from design practice and project rules, not case law.
